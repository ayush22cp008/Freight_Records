## 1. Purpose

This investigation evaluated the Reviewer Approve/Reject decision endpoint (`src/app/api/admin/review/route.ts`) to determine if it safely handles failures during the decision process, in accordance with the locked Reviewer Blueprint requirement that applicants must not be left in partially committed or contradictory states.

---

## 2. Findings: Transaction Atomicity

The current implementation performs multiple distinct, unbatched asynchronous database operations. 

**For a `REJECT` decision:**
1. `UPDATE onboarding_evidence SET status = 'REJECTED'`
2. `UPDATE freight_identities SET verification_status = 'REJECTED'`
3. `INSERT INTO reviewer_decisions (...)`

**For an `APPROVE` decision:**
1. `UPDATE onboarding_evidence SET status = 'APPROVED'`
2. `UPDATE freight_identities SET verification_status = 'VERIFIED'`
3. `INSERT INTO reviewer_decisions (...)`
4. `INSERT INTO drivers` OR `INSERT INTO companies`

Because these are executed sequentially via the standard Supabase REST client without an underlying transactional wrapper (like an RPC function), any interruption (e.g., network timeout, DB constraint violation, or Node.js process crash) will produce a partially committed state.

---

## 3. Verified Failure States

The lack of atomicity guarantees that the following failure modes **can and will** produce contradictory states:

### 3.1 Failure during Approve
If the API fails between operations:
- **Failure after step 1:** Evidence becomes `APPROVED` while Identity remains `PENDING`.
- **Failure after step 2:** Identity is `VERIFIED`, but the `reviewer_decisions` history row is missing.
- **Failure after step 3:** The decision is completely saved, but the resulting `drivers` or `companies` business record is missing. The applicant is effectively approved but unable to operate, requiring manual database intervention to repair the profile.

### 3.2 Failure during Reject
If the API fails between operations:
- **Failure after step 1:** Evidence becomes `REJECTED` while Identity remains `PENDING`. This breaks the Queue display and validation logic.
- **Failure after step 2:** Identity becomes `REJECTED`, but the `reviewer_decisions` history row is missing, violating the audit trail requirement.

---

## 4. Conclusion & Recommendation

**VERDICT: GAP (Blueprint Violation)**

The current implementation violates the Reviewer Blueprint requirement. A final decision failure can and will leave the applicant in a partially committed, contradictory state. 

**Recommended Action:**
The sequence of mutations in `src/app/api/admin/review/route.ts` must be refactored to execute atomically. Since Supabase Data API REST calls do not support multi-statement transactions directly from the Node client, the recommended solution is to move the decision logic into a Postgres Stored Procedure (RPC) and call the RPC from the route. This guarantees that either all operations succeed or all roll back safely, keeping the applicant in `PENDING` if a failure occurs.
