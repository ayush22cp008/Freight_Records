## Current Source Evidence

The current implementation constructs the password-recovery redirect as:

```text
/api/auth/confirm?next=/update-password
```

through `resetPasswordForEmail()`.

The confirmation route reads `token_hash` and `type`, then calls Supabase `verifyOtp()`. On successful verification it redirects to the `next` path; otherwise it redirects to Login with an invalid/expired recovery-link error.

The current source therefore contains an explicit failure path consistent with the observed Login redirect, but this alone does not prove why Supabase is returning the expired/invalid recovery state.

## Investigation Objective

Determine why a freshly generated recovery email link, clicked once, results in an invalid/expired recovery-link state instead of establishing a valid recovery session and reaching `/update-password`.

## Investigation Areas

Inspect and establish evidence for:

1. Exact recovery email URL generated by the configured Supabase Auth flow.
2. Whether the email link uses the expected Supabase recovery format for the current project configuration.
3. Whether the custom `/api/auth/confirm` route is compatible with the actual recovery link format.
4. Whether the application is using PKCE/code-based recovery, token-hash verification, or another recovery mechanism at runtime.
5. Whether `verifyOtp()` is being called with the correct parameters for the actual link received.
6. Redirect URL configuration in Supabase and the deployed Vercel application.
7. Whether the recovery callback loses, consumes, or mishandles required recovery parameters before verification.
8. Whether the same recovery link behaves differently when opened in a clean browser/session.
9. Whether a valid recovery session exists after the callback failure.
10. Whether the existing `/api/auth/confirm` implementation should be retained, changed, or removed in favor of the recovery mechanism actually generated by Supabase.

## Do Not Assume

Do not assume that `otp_expired` means the user waited too long. The manual evidence is specifically a fresh email + one click.

Do not assume the problem is `/update-password`; the failure currently occurs before that page is reached.

Do not replace the recovery architecture merely because the current route fails. First establish the actual runtime recovery mechanism and root cause.

## Locked Product Decisions

Once the recovery link works, the intended user experience remains:

```text
Forgot Password
→ Email reset link
→ Secure recovery session
→ Set New Password
→ Confirm New Password
→ Password updated
→ Success message
→ Login
```

The same mechanism must support Company, Driver, and Reviewer accounts.

Password reset changes the password only; it must not alter role, identity, verification status, or reviewer authorization.

No separate Change Password feature is part of this Subnode.
