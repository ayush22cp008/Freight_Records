# Driver Dashboard Trip History — Timeline Selection Investigation

**Project:** Freight — AI Builders Hackathon  
**Scope:** Historical completed-trip Timeline navigation  
**Status:** INVESTIGATION COMPLETE — implementation fix required  

## 1. Purpose

Investigate why the new Driver Dashboard `Past / Completed Trips` section successfully displays completed trips and provides a `View Timeline` link, but the Timeline page returns:

> No active trip found. Cannot display timeline.

The investigation is specifically about historical trip selection. It does not reopen Node 4 or Node 5.

## 2. Trigger / Manual Observation

Ayush manually opened the Driver Dashboard and observed completed trips under:

```text
Past / Completed Trips
```

A completed trip displayed a `View Timeline` button. The browser navigated to a URL containing a specific trip identifier:

```text
/timeline?tripId=4376665c-e7c6-41b2-98bd-373600b66b48
```

The Timeline page then displayed:

```text
No active trip found. Cannot display timeline.
```

This establishes that the Dashboard link is generating a trip-specific URL, while the Timeline page is not successfully loading that selected historical trip.

## 3. Evidence — Dashboard Behavior

The approved Driver Dashboard implementation plan requires completed trips to link to:

```text
/timeline?tripId=<id>
```

The current browser observation confirms that this URL form is actually being generated for a completed trip.

Status: **VERIFIED by Ayush manual observation.**

## 4. Evidence — Timeline Source

Current source file:

```text
src/app/(authenticated)/timeline/page.tsx
```

The Timeline page currently defines:

```typescript
export default async function TimelinePage() {
```

It does not receive or read `searchParams`, and therefore does not consume the `tripId` supplied in the URL.

The current trip lookup is effectively:

```typescript
const { data: trip } = await supabaseServer
  .from('trips')
  .select('id, facility_name')
  .eq('driver_id', driver.id)
  .in('status', ['active', 'claimed', 'in_progress', 'completed'])
  .single();
```

The source therefore selects a trip from the authenticated driver's trips by driver ownership and lifecycle status rather than selecting the exact trip requested by the Dashboard URL.

Status: **VERIFIED from current source inspection.**

## 5. Previous Timeline Bug Fix Context

An earlier Timeline bug fix changed the status restriction from only `active` to:

```text
active
claimed
in_progress
completed
```

That was necessary so a valid completed trip could be eligible for Timeline lookup.

However, that fix did not introduce URL-based trip selection. The current source still does not use the `tripId` query parameter.

Therefore, the current problem is distinct from the earlier `status = active` bug.

## 6. Root Cause

**ROOT CAUSE: The Timeline page has no trip-selection mechanism tied to the `tripId` query parameter generated by the completed-trip Dashboard CTA.**

The Dashboard now supports historical trip navigation, but Timeline still assumes it can identify the trip solely from the authenticated driver's current/eligible trip state.

This is incompatible with a driver having multiple completed trips.

The use of `.single()` also makes the lookup unsuitable when more than one matching trip exists for the driver, because the query is not constrained to the specific historical trip selected by the user.

## 7. Security / Authorization Requirement

The correct fix must not trust `tripId` by itself.

The Timeline must:

1. authenticate the current user;
2. resolve the authenticated user to the server-side `driver.id` as it does today;
3. read the requested `tripId` from the URL;
4. query that exact trip while also requiring:

```text
driver_id = authenticated driver.id
```

This preserves tenant isolation and prevents a driver from using another driver's trip UUID to access their Timeline.

The trip lookup should therefore be conceptually:

```text
trip.id = requested tripId
AND
trip.driver_id = authenticated driver.id
```

The existing allowed lifecycle statuses may remain as appropriate for Timeline visibility; the critical missing constraint is exact trip selection plus ownership.

## 8. Required Timeline Result

For a completed trip selected from `Past / Completed Trips`:

```text
Dashboard
  ↓
View Timeline
  ↓
/timeline?tripId=<completed-trip-id>
  ↓
Authenticated driver resolved
  ↓
Exact trip selected by tripId + driver ownership
  ↓
Events loaded for that exact trip
  ↓
Trip Timeline displayed
```

The Timeline must not silently substitute another trip belonging to the same driver.

## 12. Investigation Conclusion

**Observation:** Completed-trip Dashboard navigation reaches a URL containing a specific `tripId`, but Timeline reports no trip.  
**Evidence:** Current Timeline source does not read `tripId` and instead queries by authenticated driver plus status.  
**Root Cause:** Historical trip selection is missing from Timeline.  
**Decision:** Implement a focused Timeline lookup fix using the requested `tripId` together with authenticated server-resolved driver ownership.
