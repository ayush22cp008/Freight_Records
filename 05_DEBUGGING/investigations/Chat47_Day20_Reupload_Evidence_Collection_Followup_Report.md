## 1. Investigation Objective

Validate the end‑to‑end evidence collection flow for a rejected applicant who re‑uploads evidence, and confirm that the system records the new evidence correctly without creating unintended reviewer decisions.

## 2. Prompt Summary (source)

The prompt (Chat47_Day20_Reupload_Evidence_Collection_Followup.md) asks us to:
- Trace the code paths involved when a rejected applicant accesses the re‑upload page and submits new evidence.
- Verify that the backend stores the new evidence and updates the applicant’s status to `PENDING`.
- Ensure no extra `REJECTED` decision rows are inserted.
- Capture any UI or queue anomalies that could mislead the applicant or reviewer.

## 4. Findings

1. **Backend handling** – The same endpoint (`/api/onboarding/submit`) processes both fresh onboarding and evidence re‑upload. It calls `upsertApplicantEvidence` and then updates the applicant’s `status` to `PENDING`. No call to `insertReviewerDecision` occurs because the condition `if (status === 'REJECTED')` is false after the status change.
2. **Database writes** – A new row is added to `onboarding_evidence` with a fresh `id`. The `reviewer_decisions` table remains unchanged; the original rejected decision is preserved.
3. **RLS** – Policies allow the applicant to read only their own evidence and prevent them from seeing reviewer decisions. The policies are correctly scoped to `auth.uid()`.
4. **UI feedback** – After a successful upload the app redirects to `/onboarding/complete`. The page currently does **not** display an explicit *pending‑review* banner, which can cause confusion (the applicant sees no confirmation of the new pending state).
5. **Reviewer Queue** – The queue view filters on `status = 'SUBMITTED'` and `has_new_evidence = true`. Because the re‑upload updates the same `submission_id`, the `has_new_evidence` flag is not set, so the queue does not surface the pending item.
6. **History view** – The history page only renders rows from `reviewer_decisions`; newly added evidence does not appear, leading to the perception of an incomplete record.

## 5. Root‑Cause Summary

- **Missing UI confirmation** – The onboarding completion page lacks a visible indicator that the new evidence is pending review.
- **Queue filter logic** – The queue relies on a new `submission_id` rather than detecting updated evidence on the existing submission.
- **History rendering limitation** – History does not include evidence rows, so reviewers cannot see the newly uploaded material without navigating elsewhere.

## 6. Recommendations (investigation‑only, no code changes here)

- Add a banner on the completion page: *"Your new evidence has been received and is pending reviewer review."*
- Update the reviewer queue query to also consider `evidence_updated_at` newer than the latest decision timestamp.
- Extend the history component to display recent `applicant_evidence` entries alongside decisions.
