## 2. Comparison Matrix

### Reviewer Responsibility Boundary: VERIFIED
The Reviewer is strictly confined to verifying whether evidence supports a claimed identity and role. The current implementation (`/reviewer` routes) exposes no trip operations, delivery operations, or general administration tasks. The duplicate global navigation bar was also successfully removed to prevent routing outside this boundary.

### Reviewer Mental Model: VERIFIED
The implementation aligns exactly with the `Applicant + Claimed Role + Evidence -> Evaluate -> Verify -> Approve/Reject` model. The UI flow in `ApplicantVerificationClient` sequentially requires evidence examination before enabling the final approval action.

### Verification Queue: VERIFIED
The queue (`/reviewer/queue/page.tsx`) correctly lists only pending applicants. Opening a pending applicant does not alter their persistent state, and there is no persistent `Under Review` status introduced.

### Applicant Verification: VERIFIED
The `ApplicantVerificationClient.tsx` provides a dedicated workspace for one applicant, displaying their email, requested role, and evidence in a single context. Navigation strictly provides a "Back to Verification Queue" explicit control rather than a navigation trap.

### Evidence Examination: VERIFIED
A dedicated evidence viewer displays either a signed URL via an iframe or a clear error state with retry behavior. Technical failures in loading evidence do not automatically trigger an applicant rejection.

### Identity / Role Verified Action: VERIFIED
The UI explicitly implements a human-confirmation step: "Confirm: Identity / Role Verified" (line 312 in `ApplicantVerificationClient.tsx`). The final `Approve` button remains disabled until this confirmation is explicitly provided, preserving the blueprint's mandate that viewing evidence alone does not constitute verification.

### Approve / Reject Flow: VERIFIED
Separate final confirmation modals exist for both Approve and Reject. The rejection flow strictly requires a non-empty `rejectReason` before the Reject action can be submitted.

### Decision Failure Handling: VERIFIED
If the final API decision (`/api/admin/review`) fails, the frontend catches the error and explicitly sets a `serverError` state, warning the reviewer that the decision failed and the applicant remains in "Pending Verification", allowing retry.

### Decision Result: VERIFIED
Upon successful API confirmation, the UI transitions to a dedicated success state showing "Applicant Verified" or "Applicant Rejected" alongside the user's email, role, and the rejection reason if applicable, with an explicit button to return to the queue.

### Verification History: VERIFIED
The Verification History (`/reviewer/history/page.tsx`) provides a chronological list of completed verification records ordered by newest decision first.

### Read-only Completed Record: VERIFIED
Navigating into a completed record (`/reviewer/history/[id]`) presents a read-only view of the evidence via `EvidenceViewerClient`. The UI explicitly lacks any verify, approve, or reject controls.

### Evidence Type Semantics: VERIFIED
The previous implementation gap where driver evidence was mislabeled has been successfully patched. The UI now explicitly checks against `'DRIVING_LICENCE'` and properly labels it as "Driving Licence", ensuring semantic consistency with the onboarding flow.
