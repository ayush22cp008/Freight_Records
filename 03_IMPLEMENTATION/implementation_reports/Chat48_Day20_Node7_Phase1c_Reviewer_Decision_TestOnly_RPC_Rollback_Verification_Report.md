## 1. Objective

Provide a safe, isolated test mechanism to verify that the Reviewer Decision transaction cleanly rolls back when an internal failure occurs. The goal is to prove that if an exception is raised mid-transaction, all previously executed database mutations (like the evidence status update) are completely reverted, leaving the applicant in a safe `PENDING` state.

---

## 2. Implementation: Test-Only RPC

A dedicated test function has been created that exactly mirrors the production logic but deliberately raises an exception immediately after updating the evidence status (and before updating the identity or recording the decision).

- **File Created:** `src/db/migrations/013_reviewer_decision_test_rpc.sql`

**Safety Assurances:**
- The production RPC (`process_reviewer_decision`) remains completely untouched.
- No production API routes call this test function.
- The test function is strictly opt-in via manual database/API execution.

## 3. Manual Verification Steps

Because this environment connects directly to the production database and lacks an automated CI test database pipeline, you must execute this test manually using a dummy applicant to ensure production safety.

**Step 1: Deploy the Test RPC**
1. Open the Supabase SQL Editor.
2. Run the SQL script from `src/db/migrations/013_reviewer_decision_test_rpc.sql`.

**Step 2: Execute the Rollback Test**
1. Identify a dummy `PENDING` applicant's UUID (e.g., `12345678-1234-1234-1234-123456789012`).
2. Run the following command in the Supabase SQL Editor to trigger the test function:
   ```sql
   SELECT process_reviewer_decision_test('12345678-1234-1234-1234-123456789012', 'APPROVE', NULL);
   ```

**Step 3: Observe the Results**
1. You will receive an error: `Simulated Rollback Failure (Approve path)`.
2. Inspect the `onboarding_evidence` table for that applicant. **The evidence `status` should still be `PENDING`**, despite the `UPDATE onboarding_evidence SET status = 'APPROVED'` statement occurring *before* the exception in the code.
3. Inspect the `freight_identities` table. The `verification_status` should still be `PENDING`.

This experimentally proves that the PostgreSQL transaction boundary behaves atomically.

**Step 4: Cleanup**
