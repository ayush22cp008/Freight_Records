## 1. Objective

Fix the authenticated applicant onboarding page so that a recovered (re-uploaded) rejected applicant is correctly shown the Pending Verification UI instead of falling through to the Complete Onboarding form.

The root cause: the page previously performed an applicant-wide .single() evidence lookup, which fails when multiple evidence rows exist (old rejected + new pending). The fix applies the same safe deterministic pattern already used in the Reviewer Verify page (Phase1b).

---

## 2. Files Modified

### src/app/(authenticated)/onboarding/page.tsx

**Before:**

The evidence query used .single() and gated on truthy evidence AND non-REJECTED status:

  const { data: evidence } = await supabase
    .from('onboarding_evidence')
    .select('*')
    .eq('auth_id', identity.auth_id)
    .single();

  if (evidence && identity.verification_status !== 'REJECTED') {

**After:**

Evidence query now deterministically selects the newest PENDING row, and state gate uses identity lifecycle status as the primary condition:

  const { data: evidenceRows } = await supabase
    .from('onboarding_evidence')
    .select('*')
    .eq('auth_id', identity.auth_id)
    .eq('status', 'PENDING')
    .order('created_at', { ascending: false })
    .limit(1);

  const evidence = evidenceRows?.[0] ?? null;

  if (identity.verification_status === 'PENDING') {

Additional changes in the Pending Verification UI block:
- evidence.document_type replaced with evidence?.document_type with 'Unknown' fallback
- evidence.status replaced with evidence?.status with 'PENDING' fallback
- evidence.rejection_reason replaced with evidence?.rejection_reason (optional chaining)
