## B. Driver ID / Driver Code Evidence
- **Generation:** Generated via a Postgres sequence (`driver_code_seq` starting at 10) and a `BEFORE INSERT` trigger function (`generate_driver_code`).
- **Format:** `DRV` followed by 3 digits (e.g., `DRV010`). [VERIFIED]
- **Uniqueness Constraints:** Enforced at the database level by a `UNIQUE` constraint on the `driver_code` column in the `drivers` table (from `001_create_core_tables.sql`).
- **Legacy Sequential IDs:** The legacy sequential Driver IDs remain active and are actively generated by this migration. The system has not transitioned to random IDs.
- **Exposure:** It is treated as a username/identifier (passed in login payload), not a secret.
- **Migration Status:** `004_auto_generate_driver_code.sql` is **LOCAL ONLY** (untracked).

## D. RLS / Service-Role Evidence
- **RLS State:** RLS is enabled on the `drivers` table.
- **Service-Role Usage:** Server-side API routes use a dedicated client (`supabaseServer` in `src/lib/supabase-server.ts`) initialized with `process.env.SUPABASE_SERVICE_ROLE_KEY`.
- **Boundary Verification:** The `service_role` client is strictly imported in server routes (`api/auth/login`, `api/events/arrival`, etc.) to bypass RLS for driver lookups and inserts. The credentials do not reach browser/client code.

## E. Role Enforcement Evidence

- **Implicit Role Behavior:** The system hard-codes the assumption that every authenticated user is a Driver. API routes unconditionally lookup a `drivers` record using `auth.user.id` and return a 401 error if not found.
